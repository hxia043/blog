# 2. 分库分表是什么意思？为什么分库分表？

```
**分库分表**是 MySQL 数据库中一种常见的优化策略，主要用于在数据量过大时，通过分散数据存储和查询压力来提升性能和可扩展性。

### 1. 什么是分库分表？

- **分库**：将数据按一定规则拆分到不同的数据库中。比如，将一个电商系统的数据分成多个数据库，每个库存储不同的业务模块（如订单库、用户库等），或者将一个表的数据分布到多个库中。
- **分表**：将一个大表按某种规则（例如用户 ID、日期等）拆分成多个小表。分表可以在同一个库中，也可以分布到不同的库中。
- **分库分表结合**：既分库又分表，将数据分散到多个数据库的多个小表中，以进一步降低单库单表的压力。

### 2. 为什么需要分库分表？

当数据库的数据量和访问量逐渐增加时，会遇到以下问题：

- **单表容量过大**：MySQL 单表数据量达到百万甚至亿级时，查询、更新、删除等操作的性能会显著下降，维护和备份也会变得困难。
- **I/O 性能瓶颈**：随着数据量和访问量增加，数据库的磁盘 I/O 和网络 I/O 压力会加大，进而影响响应速度。
- **锁竞争增加**：高并发情况下，单表的锁竞争会变得严重，导致事务等待时间增加，从而影响系统的吞吐量。
- **扩展性不足**：单一数据库实例的存储和计算资源是有限的。分库分表可以横向扩展（Scale-Out），让更多数据库实例分担存储和查询压力。

### 3. 分库分表的好处

- **提升查询性能**：将一个大表拆分成多个小表或多个库后，每个表的数据量更小，查询和索引扫描的效率更高。
- **减轻单库压力**：通过分库分表，可以将数据和查询分布到不同的数据库实例上，减轻单库的 CPU、内存和 I/O 压力。
- **提升并发性能**：由于不同表或库可以部署在不同的服务器上，可以利用多台服务器分担并发请求，提升系统的整体吞吐量。
- **便于数据归档**：分表策略可以根据时间等规则将历史数据存放到不同表中，方便数据的归档和管理。

### 4. 分库分表的常见策略

- **按范围分表**：根据字段值范围（如 ID 范围）将数据分配到不同表或库。
- **按哈希分表**：将特定字段（如用户 ID）进行哈希运算，然后根据哈希值将数据分配到不同的表或库中。
- **按日期分表**：对于时间序列数据，如订单和日志表，可以根据日期（月、年等）将数据分表存储。

### 5. 分库分表的缺点

分库分表也带来了复杂性：

- **事务处理复杂化**：分布式环境下跨库的事务处理较为复杂，MySQL 不原生支持分布式事务。
- **查询复杂度增加**：需要在多个表或库中查找数据，且要处理跨库查询、分页等操作，代码和逻辑更复杂。
- **数据一致性维护**：数据的分布式存储增加了保持一致性的难度。
- **运维成本增加**：多库和多表的备份、迁移和监控变得更复杂，数据管理成本增高。

### 总结

分库分表是一种用来提升 MySQL 数据库性能和扩展性的策略，适用于大数据量和高并发的场景。它通过数据分散来减轻单一数据库的压力，但也带来了系统设计和运维上的复杂性。
```

# 4. auto_increment 是线程安全的吗？

```
在 MySQL 中，`AUTO_INCREMENT` 是**线程安全**的。MySQL 为 `AUTO_INCREMENT` 列提供了内部机制，确保在多线程或并发环境中生成的值不会发生冲突。具体机制如下：

1. **InnoDB 存储引擎**：
   - 在 `InnoDB` 中，`AUTO_INCREMENT` 的值由表级锁（table-level lock）保护，保证同一时间只有一个线程可以插入具有 `AUTO_INCREMENT` 列的行。
   - 每当一个插入操作请求 `AUTO_INCREMENT` 值时，InnoDB 会在内存中缓存一个范围值，并逐步分配给插入操作，从而减少频繁写入磁盘的开销。

2. **MyISAM 存储引擎**：
   - 在 `MyISAM` 中，`AUTO_INCREMENT` 依赖表级锁的控制。即便有多个线程并发插入，MyISAM 会通过加锁来保证 `AUTO_INCREMENT` 的唯一性和顺序性。
   - 通过这种锁定机制，即使在并发环境中，`AUTO_INCREMENT` 值依然是安全且唯一的。

3. **全局和会话级锁**：
   - 在高并发情况下，MySQL 使用会话级锁管理不同的 `AUTO_INCREMENT` 请求，确保没有线程可以在没有锁的情况下读取或分配重复的 `AUTO_INCREMENT` 值。

4. **事务隔离性**：
   - 在事务环境中，InnoDB 支持隔离级别，确保在事务回滚后，不会影响已分配的 `AUTO_INCREMENT` 值。尽管回滚不会回收已分配的值，但仍保证每个提交的数据唯一性。

### 总结
MySQL 的 `AUTO_INCREMENT` 是线程安全的，无论是单实例还是多线程插入情况下，都不会出现冲突。通过锁机制和缓存管理，即使在高并发情况下，`AUTO_INCREMENT` 的唯一性和顺序性都能得到保证。
```

# 使用 mysql 的好习惯？

下面是许多SQL程序员使用UPDATE或DELETE时所遵循的习惯。  
❑ 除非确实打算更新和删除每一行，否则绝对不要使用不带WHERE子句的UPDATE或DELETE语句。  
❑ 保证每个表都有主键（如果忘记这个内容，请参阅第15章）​，尽可能像WHERE子句那样使用它（可以指定各主键、多个值或值的范围）​。  
❑ 在对UPDATE或DELETE语句使用WHERE子句前，应该先用SELECT进行测试，保证它过滤的是正确的记录，以防编写的WHERE子句不正确。  
❑ 使用强制实施引用完整性的数据库（关于这个内容，请参阅第15章）​，这样MySQL将不允许删除具有与其他表相关联的数据的行。

LIKE 为什么要写最右？

正如所见，MySQL的通配符很有用。但这种功能是有代价的：通配符搜索的处理一般要比前面讨论的其他搜索所花时间更长。这里给出一些使用通配符要记住的技巧。  
❑ 不要过度使用通配符。如果其他操作符能达到相同的目的，应该使用其他操作符。  
❑ 在确实需要使用通配符时，除非绝对有必要，否则不要把它们用在搜索模式的开始处。把通配符置于搜索模式的开始处，搜索起来是最慢的。  
❑ 仔细注意通配符的位置。如果放错地方，可能不会返回想要的数据。  

不要忘了WHERE子句 应该保证所有联结都有WHERE子句，否则MySQL将返回比想要的数据多得多的数据。

性能考虑 MySQL在运行时关联指定的每个表以处理联结。这种处理可能是非常耗费资源的，因此应该仔细，不要联结不必要的表。联结的表越多，性能下降越厉害。
